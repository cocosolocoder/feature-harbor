# FeatureHarbor

产品意见与公开路线图。

需要Node.js 24 或更新版本。直接运行 TypeScript，不需要安装其他包。

查看命令帮助：

```sh
node server.ts --help
```

启动本地服务：

```sh
node server.ts serve --host 127.0.0.1 --port 8080 --data-dir data
```

打开 http://127.0.0.1:8080 查看首页。Ctrl+C 停止服务。`--data-dir` 指定本地业务数据目录，重启时继续使用同一目录。

接口：

- `GET /health` 返回服务状态和产品名称。
- `GET /api/ideas` 返回意见列表（`{ideas: [...]}`），最新的意见排在最前。
- `POST /api/ideas` 提交新意见，请求体为 JSON 对象：`title`（必填，去掉首尾空白后非空、最多 120 字）、`description`（必填，须含非空白内容、最多 5000 字）、`scenario`（可选字符串，省略视为空、最多 1000 字），长度按 Unicode 码点计算。成功返回 201 和 `{idea: {...}}`，包含 `id` 与 `createdAt`；字段缺失、类型或内容不合要求返回 400。请求正文必须能完整按 UTF-8 解码：已完整送达且未超过 1000000 字节的正文含非法 UTF-8（单独的续字节、缺少后续字节的多字节字符、不符合 UTF-8 规则的编码，无论出现在哪个字段还是正文其他位置）时整次提交返回 400、`error` 为“请求体不是有效的 UTF-8”，不替换、不删字节、不保存正常片段；用户主动输入的“�”以合法 UTF-8（EF BF BD）编码时是普通文字，照常处理。错误先后关系：超过 1000000 字节仍报“请求体过大”（即使同时含非法编码），编码有效但 JSON 格式错误仍报 JSON 错误，字段问题仍报字段错误。
- 未知路径返回 404，已知路径不支持的方法返回 405。
- 首页 `/` 提供提交表单和意见列表，数据保存在 `--data-dir` 指定的目录中，重启后保留。
- 首页意见列表支持关键词搜索（纯页面行为，不经过接口）：输入完整关键词后点击“搜索”，标题、详细说明或使用场景任一字段包含该段文字（去掉关键词首尾空白、英文大小写不敏感）的意见按原顺序显示；关键词内部空格、标点、尖括号与正则样文字都按普通文字逐字比较，不拆词。空白关键词执行搜索或点击“清空”恢复完整列表。搜索不过滤已保存记录、不发起请求、不影响提交表单草稿；完整列表为空时仍提示“还没有意见记录”，有记录但无匹配时提示“没有找到符合关键词的意见”。

字段规则（必填、空白处理与字符上限）只在 `idea-fields.ts` 维护一次：接口直接调用它，首页无法使用模块导入，由 `server.ts` 把同一份函数源码注入内联脚本，因此页面说明、两个入口的提示与实际保存判定始终一致；长度统一按 Unicode 码点（`Array.from(text).length`）计算。


```sh
curl http://127.0.0.1:8080/health
curl http://127.0.0.1:8080/api/ideas
curl -X POST http://127.0.0.1:8080/api/ideas \
  -H 'content-type: application/json' \
  -d '{"title":"支持深色模式","description":"希望界面支持深色模式。","scenario":"夜间使用"}'
```

## 自动化测试

无需安装任何依赖，直接运行：

```sh
node --test
```

- `test/page.test.ts`：前端回归测试。启动真实服务并 GET `/`，取出页面中的内联脚本原文，在带极简 DOM 与可控 fetch 的 `vm` 沙箱中执行，精确控制首次列表请求与提交请求的成功、失败及返回先后。覆盖：
  - 提交先返回 / 列表先返回两种次序下，已保存意见始终可见且排在已有记录之前；
  - 晚到的列表响应不会覆盖已提交意见，两个响应都包含同一条时按 `id` 只显示一次；
  - 标题、正文相同但 `id` 不同的意见分别显示，不按文字内容合并；
  - 同页连续提交两条时后提交的排最前，与两个响应返回的先后无关（返回次序颠倒时先提交的后补入后提交的之后），每条记录标题、详细说明、非空使用场景与提交时间逐条对应；
  - 加载中不显示“还没有意见记录”，加载成功且确为空才显示；首次加载失败显示加载失败提示且不被后续提交成功清除；
  - 提交失败（网络错误、非 2xx、非法响应体，或响应可解析且为 201 但整体不含 idea、idea 为空值/数组/字符串、id 为空或非字符串、标题/详细说明/使用场景/提交时间缺失或非字符串）保留表单内容、不插入列表、不显示成功提示，已有记录的数量、顺序与内容保留；结构异常后继续编辑并再次提交收到完整记录时仍按成功处理，实际返回的意见排最前、清空等待期间未编辑的表单；scenario 为空字符串是正常边界，与缺少 scenario 字段区分；
  - 成功或失败提示只属于最近一次点击提交，不按响应返回先后归属：发起新提交先清除上一条提示；上一条请求仍在途时，较早请求迟到的网络错误、服务拒绝、响应无法解析或内容不完整都不能把后一次的成功改成失败，较早请求迟到成功也不能在后一次的失败提示或新一次等待旁边再显示成功；最近一次点击若被表单校验直接拦下，字段错误同样保留，不被旧请求结果掩盖；
  - 过期但已确认保存的请求仍把意见（含自己的标题、详细说明、使用场景与时间）并入列表，不因提示归属而丢弃；草稿是否清空仍只取决于等待期间是否编辑；
  - 前端字段校验不发请求。
  - 纯文本展示：标题、详细说明与使用场景中的网页标记样文本（`<b>重点</b>`、脚本、事件属性、链接与表单片段）和实体原文（`&lt;`、`&amp;`、引号、尖括号）在首次加载与提交成功两种展示路径下逐字按普通文字显示——连同尖括号一起读到，不解析为网页结构（沙箱 DOM 记录所有创建的元素并设 innerHTML 警戒：不创建额外元素、不触发额外请求、不经过 innerHTML），不删改原文符号，实体不解码也不再叠加转义；特殊文字与普通意见混排时不影响相邻记录、排列与表单继续提交，空字符串场景仍不显示使用场景段；
  - 关键词搜索：关键词只在客户端过滤当前已合并的完整列表（不发请求、不重新拉取、不改变接口返回与已保存记录、不碰提交表单草稿与字段校验），覆盖三字段任一字段命中、英文大小写不敏感、首尾空白忽略、内部空格按整段原文不拆词、标点/尖括号/正则样文字按普通文字逐字匹配、沿用原顺序、同 id 只显示一次而同文不同 id 分别保留、空关键词与“清空”恢复完整列表；区分三种空态（加载成功且完整列表为空仍显示“还没有意见记录”、有记录但无匹配显示“没有找到符合关键词的意见”、首次列表未返回不提前断言、加载失败继续显示加载失败提示）；搜索生效后迟到的首次列表与本页新确认保存的意见（含不符合关键词暂时不可见的）继续按已生效关键词更新，清空搜索后全部已保存意见按原顺序出现。
  - 历史内容读取兼容：首次加载的记录只要结构完整，即使标题、详细说明、使用场景超过当前上限（120/5000/1000 码点，含恰好超出一个码点、长内容不截断），或标题、详细说明为空字符串/纯空白，也全部按原文渲染——不出现“意见列表加载失败”或“还没有意见记录”，不跳过特殊记录、不只显示混排其中的普通意见，空白不替换成默认文字；历史标题首尾空白、说明与场景中的换行、中文、表情保留，尖括号与网页标记样文本继续按普通文字展示（不解析、不走 innerHTML），不能解析为日期的时间字符串按原文显示；scenario 为空字符串继续省略场景段落，并与缺少 scenario 字段（整次加载失败、不部分展示）区分；读入后提交符合当前规则的新意见照常成功并排最前，旧记录内容与相对次序不变；表单对超限或空白的新内容仍在发请求前拦截，已加载历史记录的数量、顺序与内容不变；结构完整的超限记录与缺字段/空 id/类型错误记录混排时仍整次加载失败，不为接受超限旧内容放宽结构判定。
- `test/length-limits.test.ts`：三个字段字符上限在接口与首页表单两个入口的回归，长度按 Unicode 码点计算（标题 120、详细说明 5000、使用场景 1000）。接口侧真实起服务走 `POST/GET /api/ideas`，首页侧通过 `page.test.ts` 的沙箱执行内联脚本，两侧用同一批边界内容。覆盖：
  - 中文、英文字母、单个“😀”各算一个码点；旗帜“🇨🇳”、ZWJ 表情“😮‍💨”、组合字符“é（e+组合重音）”等由多个码点组成的文字按各自码点累计——能发现把表情算成两个字符（按 UTF-16 码元）或按传输字节计数的变化；
  - 三个字段分别恰好达到自己的上限（其他内容合法）时允许提交；任一字段只多出一个码点时明确拒绝，不截断保存；
  - 标题在判断长度和保存前去首尾空白、内部空白计入；详细说明的首尾空白与换行计入长度并原样保存（被空白推到超限必须拒绝）；使用场景按原文计算与保留，省略或空字符串仍可提交；
  - 表单侧：合法边界确认保存后显示成功提示、展示实际保存的意见、未继续编辑时三框清空；超限在发出请求前显示对应字段错误、保留全部输入、不增加列表记录、无成功提示；把超限字段缩短到允许范围后可正常提交，之前的错误不继续阻止保存；
  - 接口侧：合法边界返回 201 且列表可读到完整内容；超限返回 400 和明确错误，已有意见的内容与顺序不受影响。
- `test/body-size-limit.test.ts`：整份请求体 1000000 字节大小上限的端到端回归。真实起服务走公开的 `POST/GET /api/ideas`，除普通请求外直接用原始 TCP 连接发分段请求（`fetch` 无法控制 `Transfer-Encoding: chunked` 分段，也无法把一个多字节字符的 UTF-8 字节拆到相邻两次写入），覆盖：
  - 大小按实际传输的 UTF-8 字节数累计，JSON 的字段名、括号、引号与字段外空白都计入，中文（3 字节）、表情（4 字节）不按一个字符当一个字节——用 3 字节中文填充使整份超过 1000000 字节但 JS 字符数不足 1000000 的用例，区分按字节与按字符计数；这套字节限制与三个字段按 Unicode 码点的字符上限分别验证、互不混淆（字段按码点超限仍报字段错误，不是“请求体过大”）；
  - 三个意见字段符合现有规则、整份 JSON 合法且正文恰好 1000000 字节（Content-Length 与 chunked 各一条）返回 201 和完整保存结果，随后查询能读到原样保存、排在最前的新意见；999999 字节同样接受，边界是严格大于而非四舍五入；只多一个字节返回 400、`error` 为“请求体过大”、不带 `idea`；
  - 合法边界请求中的中文、表情与 ZWJ 表情即使在传输时被 UTF-8 字节边界拆到相邻 TCP 写入/分块（拆在 3/4 字节序列的第 1、2 个字节之后），最终保存的文字也完整，无替换字符、无丢字；
  - Content-Length 明确声明与不预告总长度的 chunked 请求走同一判定：chunked 超限既覆盖发生在中途（1200000 字节正文、每段 180000，越过上限后还有一整段），也覆盖直到最后一段才越过（前缀本身已经是一份完整合法意见、每段仅 100000 字节），还覆盖每段只有 4096 字节的小分段累计超限——不能因单段较小或前缀像完整意见就接受整次提交；
  - 超限后客户端慢速发完全部正文并保持连接等待，收到的是完整、按 `content-length` 可解析的 400 JSON，而不是连接断开或半截响应；正文同时存在 JSON 格式问题时仍报告“请求体过大”，不被格式错误覆盖；恰好 1000000 字节或更小的非法 JSON 继续返回现有的“请求体不是有效的 JSON”；
  - 被拒绝的请求不入库：原有意见（含首尾/内部空白、换行、中文、表情，以及同标题但不同 `id` 的两条）的数量、顺序、`id`、`createdAt` 与文字逐字保留，不新增截断记录、不保存已收到的前缀，`ideas.json` 与请求前逐字节一致且不残留 `.tmp`。
- `test/invalid-utf8.test.ts`：请求正文 UTF-8 编码完整性的端到端回归。真实起服务，用原始 TCP 连接发送 `fetch` 无法表达的非法字节与跨段拆分（同 `body-size-limit` 的方式），覆盖：
  - 已完整送达且未超 1000000 字节的正文含非法 UTF-8 时返回 400、`error` 为“请求体不是有效的 UTF-8”，响应不带 `idea`、不新增意见；非法字节分别放在标题、详细说明、使用场景、额外字段值、字段外位置与正文末尾，均按整次提交失败；
  - 覆盖三类非法形态：单独出现的续字节（0x80/0xBF/0xFF）、缺少后续字节的多字节字符（E4 B8、F0、F0 9F 98）、不符合 UTF-8 规则的编码（过长 C0 AF、代理区 ED A0 80、超范围 F5 80 80 80）；字符串内部的非法字节特意构造成“被替换成“�”后仍是合法 JSON 且字段合规”的形态——旧实现正是因此误回 201 并保存被改写的原文；
  - 非法字节慢速拆成多段送达（Content-Length）与 chunked 分段都拒绝：判定基于整份正文拼接后的字节，分段本身不构成损坏；
  - 用户主动输入的“�”以合法 UTF-8（EF BF BD）编码时按普通文字接受：201、标题按原规则去首尾空白、三字段逐字保存，列表随后读到相同内容，不凭该字符拒绝或替换；
  - 合法多字节字符（中文、表情、ZWJ 表情）的 UTF-8 字节被拆在相邻 TCP 写入或 chunked 段之间时，只要整份最终完整且编码有效，Content-Length 预声明与 chunked 两种发送结果一致：201、无替换字符、无丢字，列表读到逐字相同的内容；
  - 错误先后关系：正文超过 1000000 字节且同时含非法编码仍报“请求体过大”；未超限、编码合法但 JSON 非法仍报“请求体不是有效的 JSON”；编码合法但字段不合要求仍报字段错误；每次失败后原有意见的数量、顺序、`id`、`createdAt` 与文字逐字保留，磁盘不残留 `.tmp`。
- `test/interrupted-request.test.ts`：请求中途断开（整次请求的正文未接收完整就失去连接）时不保存的端到端回归。真实起服务，除公开的 `POST/GET /api/ideas` 外直接用原始 TCP 连接制造 `fetch` 无法表达的发送形态（明确声明长度却少发字节、chunked 不发结束标记），覆盖：
  - 被中断的那条意见本身三个字段符合当前标题、详细说明与使用场景规则、整份请求体远低于已有大小上限，完整发送时按现有行为返回 201 保存——保证“没保存”只能来自未完成接收而不是内容被拒；
  - `Content-Length` 明确声明整份长度却只发其中一部分（断在说明字段中间、只有开头一小段）随后以 FIN 正常关闭或 RST 直接复位：不保存；
  - 已收到的前缀恰好是一份可解析 JSON、三个意见字段都已完整且内容合法（声明长度比实发多一截）时，FIN 与 RST 两种断开都不能因为“文字看起来完整”就提前解析并保存；分段慢速发送、表情的 UTF-8 字节拆在相邻两次写入也不改变这一结论；
  - `Transfer-Encoding: chunked` 下意见全部文字已逐块发完、只缺“0 长度分块”这一请求结束标记就断开（FIN 与 RST 各一），同样属于未完成提交，不入库；
  - 数据保护：中断前后已有意见的数量、顺序、`id`、`createdAt` 与三个文字字段逐字保持，说明和场景中的空白、换行、中文与表情不被改写，同标题同正文的两条仍是不同标识的独立记录；正式保存内容不被清空、重写或混入收到的前缀，不残留本次提交的 `.tmp`；
  - 没有任何意见时发生中断：列表仍成功返回空数组（不能变成读取失败），磁盘保持初始的 `[]`；连接已经断开，不断言客户端必须收到某种错误响应，关键结果是没有保存；
  - 中断之后服务继续接受其他请求：查询正常，再完整提交同一条合法意见仍返回现有的 201 和完整保存结果，新意见排在已有意见之前，原有记录的内容与相对顺序不变；完整送达但内容不合法（如标题只有空白）仍按已有规则返回 400，中断保护不放宽任何内容判定。
- `test/server.test.ts`：真实起一份 `server.ts`（端口 0、临时数据目录）的端到端冒烟测试，覆盖 `/health`、首页入口与初始 `hidden` 状态、`GET/POST /api/ideas` 的契约与字段校验、同文不同 `id`、404/405。
- `test/persistence.test.ts`：意见保存的持久化回归。通过公开的 `POST/GET /api/ideas` 提交后，以 SIGTERM 正常停止服务并用同一 `--data-dir` 再次启动，覆盖：
  - 多条意见重启后数量、每条记录的全部字段（含 `id` 与 `createdAt`）与排列次序保持不变，后提交的仍在前面；
  - 标题和详细说明相同但 `id` 不同的意见重启后仍是两条独立记录，标识与提交时间不会重新生成；
